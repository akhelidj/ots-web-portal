# F0.1.2 Offline Runtime Foundation

## Overview

This ticket establishes the offline-first infrastructure for the OTS Portal. It ensures that internal users can operate the application without network connectivity by utilizing Service Workers for the app shell, IndexedDB for local data persistent, and an Outbox queue for offline mutations.

## Storage Schema and Usage

All domain data reads and offline interactions occur against IndexedDB via the `DbService`. Local storage is strictly reserved for tiny, non-domain elements (e.g., auth tokens).

The offline store uses the following IndexedDB objects:

1. `inspection_reports`: Keyed by `id`, stores local copies of inspection reports.
2. `serial_numbers`: Keyed by `id`, maps drill pipe serial values to their parent `inspectionReportId`.
3. `outbox`: Keyed by `id`, contains offline mutations awaiting dispatch to the API endpoint.
4. `meta`: Keyed by `key`, stores DB metadata such as schema versions.

### Repositories

Data access is brokered through explicit, CRUD-only repository services:

- `InspectionReportLocalRepo`
- `SerialNumberLocalRepo`
- `OutboxLocalRepo`

## Outbox Pattern & Mutation Rules

To support offline operation, features **must not** construct UI operations based solely on synchronous HTTP calls.

**Feature Ticket Rules for Mutations (F0.1.4+):**

1. **Write Local First:** Apply the intended mutation to the corresponding local IndexedDB repository so the UI reflects the change immediately.
2. **Enqueue Mutation:** Package the API request into an `OutboxItem` and call `OutboxService.enqueue()`.
   - Ensure an `idempotencyKey` UUID is generated and provided.
   - Specify the `entityType` and `operation`.
3. **Read Local:** The UI state should always mirror the data queried from the local repository.

### Format

```typescript
interface OutboxItem {
  id: string; // UUID for the queue item
  idempotencyKey: string; // UUID to prevent duplicate API executions
  createdAt: string; // ISO datestring
  entityType: string; // e.g. "InspectionReport"
  entityId: string; // The affected entity ID
  operation: string; // "CREATE", "UPDATE", "TRANSITION", etc.
  payload: any; // The exact JSON payload intended for the remote API
  status: 'PENDING' | 'SYNCED' | 'FAILED' | 'CONFLICT';
  attemptCount: number;
  lastError: string | null;
}
```

## Sync Strategy

The background sync algorithm orchestrates pending queue items when the application is open and network connectivity is (`isOnline === true`).

1. **Sequential Execution:** The `OutboxService.processQueue` executes oldest items first based on `createdAt`.
2. **Conflict Halting:** If an item fails due to a conflict (e.g. 409 API response), its status becomes `CONFLICT`. The loop halts completely until the conflict is manually addressed to prevent inconsistent sequential state.
3. **Retries:** Simple retry loops execute during online transitions for items marked `FAILED` or remaining `PENDING`.

## Manual Verification Steps

1. Prepare a production build with `npm run build:portal`.
2. Serve the build statically using any web server like `npx http-server dist/portal/browser`.
3. Load the app in a modern browser and wait a moment for the service worker caching to complete.
4. Ensure the dev-only button "Simulate Mutation" is hidden (as expected for production).
5. Open DevTools, navigate to the Network layout, and select **Offline**.
6. Refresh the page: the application should render the shell completely offline and display an "Offline" badge.
7. Repeat the steps in development mode `npm run start:portal` to interact with the "Simulate Mutation" payload end-to-end and test the indicator counter.
