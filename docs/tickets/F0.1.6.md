# Ticket F0.1.6: Auth UI for Demo and Dev

## Objective
Make the portal usable end-to-end in the browser by introducing explicit `Login` and `Change Password` mechanics. The flow strictly adheres to the default-deny and multi-tenant security baseline, guaranteeing temporary passwords enforce a rotation before granting access.

## Backend (NestJS API)
*   **Added `POST /auth/change-password`**: This endpoint requires a valid JWT (`@UseGuards(AuthGuard('jwt'))`). It validates the provided `currentPassword`, hashes the `newPassword`, sets `mustChangePassword` to `false`, revokes all existing refresh tokens for that session, and finally issues and returns a fresh pair of tokens directly to the client.
*   **Token Rotation Stability**: The core rotation strategy maintains the 7-day TTL configured originally.

## Frontend Routing Flow
The Angular portal route guards have been redesigned to provide a deterministic flow:

1.  **Entry Point (`/`)**: A dedicated `LandingComponent` intercepts the empty URL. 
    *   If Unauthenticated &rarr; Navigates to `/login`.
    *   If Authenticated & `mustChangePassword === true` &rarr; Navigates to `/change-password`.
    *   If fully Authenticated &rarr; Navigates to the default role landing (e.g., `/admin`).
2.  **`AuthGuard`**: Attached to all protected routes (Admin, Receiver, etc.). If no valid session is found, returning a `UrlTree` explicitly redirects the user to `/login`.
3.  **`MustChangePasswordGuard`**: Attached to the login route and all protected routes. If `SessionService.mustChangePassword` is true, any navigation attempt (including to `/login`) is strongly redirected to `/change-password`. If false, attempts to visit `/change-password` are redirected safely back to `/`.

## Session Strategy
*   The `SessionService` persists the `accessToken`, `refreshToken`, and a stringified `session_profile` object in `localStorage`. 
*   `mustChangePassword$` relies explicitly on the stored `session_profile`, treating the backend Login/ChangePassword response as the authoritative source of truth over the static JWT payload.
*   The **Sign Out** button in the Shell header triggers a clean wipe of these three `localStorage` keys and pushes the user back to `/login`. *IndexedDB offline data remains completely intact.*

## Offline Resilience
*   The `LoginComponent` and `ChangePasswordComponent` proactively disable interaction and display clear warning banners if `navigator.onLine` evaluates to false. 
*   If a user is already authenticated and subsequent network requests fail, the application retains its offline capacity (as tokens remain valid in `localStorage` and routes are accessible). Only fresh authentication flows enforce online connectivity.
