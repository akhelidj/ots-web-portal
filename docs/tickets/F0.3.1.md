# F0.3.1 - Child Reports MVP (Offline-First)

## Context

This feature enables the creation of Child Reports (e.g., REWORK, SCRAP, HOLD) when a `SerialNumber` fails its initial inspection. It relies on the pre-existing `disposition` captured inside the serial number's `inspectionData`.

## Architecture & Data Flow

- **Database Approach:**
  - `schema.prisma` was mutated exclusively through _additive_ changes: injecting `ChildReportType` enum, linking `ChildReport` to `Tenant` and `SerialNumber`, and introducing robust tracking fields (`version`, `tenantId`, `type`, `notes`).
- **Backend API Rules (Server-Authoritative):**
  - **Tenant Scoping:** Applied strictly across every single database query. `POST` does deep validation fetching the `InspectionReport` bounded to `tenantId` AND requiring the `SerialNumber` within that result.
  - **Idempotency:** `POST` relies on a client-supplied UUID with a pure implementation of `findUnique + if exists return 200`. Avoids `409` conflict loops on offline outbox retries. Returns `version=1`.
  - **Concurrency:** `PATCH` demands the current `version`. Rejections throw `409 Conflict`.
  - **Lock Gate:** Both `POST` and `PATCH` proactively query the Parent `InspectionReport` status, throwing `400` if `APPROVED` or `CLOSED`.
  - **Mismatch Trap:** `POST` analyzes `SerialNumber.inspectionData.disposition`, enforcing that `REWORK` creation explicitly matches a `REWORK` disposition.
- **Frontend Offline Pipeline:**
  - Uses `child-report-local.repo.ts` over IndexedDB to persist UI state eagerly.
  - Maps `CR_CREATE` and `CR_UPDATE` into the `SyncDispatcherService`.
  - Upon sync, it destroys the local entity and replaces it dynamically with the server response bridging local states to remote `version` assertions elegantly. Discards IDs via Remap streams cleanly for dependent Sync Ops.
  - `400 BadRequest` errors explicitly halt outbox loop polling on that item and drop the `syncState` of the element into `ERROR` visually.

## Manual Verification Scenarios

**Scenario 1: Offline Creation Success**

- Open Portal and navigate to a Draft Inspection Report.
- Use `Inspect` on a Serial Number and apply the `REWORK` disposition. Save offline.
- Click `Create CR`. Fill notes, click submit. Observe the Child Report listed underneath the Serial Number colored yellow `PENDING`.
- Refresh browser, reconnect API. Watch the background sync seamlessly change State to `SYNCED`.

**Scenario 2: Parent Lock Denial**

- Create a Child Report offline and leave it in `PENDING` outbox.
- Bypass UI protections and use an API tool to transition the parent Inspection Report to `APPROVED`.
- Trigger the outbox dispatcher.
- The `POST` will fail dynamically with HTTP 400 because the parent is locked. Check UI to see the sync tag visually map to `ERROR`.

**Scenario 3: Disposition Mismatch (Database Hack Simulation)**

- Set a SN offline disposition to `PASS`.
- Use a hack (e.g. DOM manipulation/console API) to enqueue a `CR_CREATE` for `REWORK` pointing to that SN.
- Let the outbox sync run. The Sync will fail via HTTP 400 (disposition mismatch logic). The loop securely halts and transitions the local entity to `ERROR`.
