# Ticket F0.1.5: Admin Customers MVP (Offline-First)

## Objective

Enable Admins to manage Customers with a fully offline-capable UI and a deterministic sync pipeline, mirroring the F0.1.4 User management architecture.

## Schema Changes (`Customer` model)

The `Customer` Prisma model has been enhanced with:

- `code`, `email`, `phone`, `addressLine1`, `addressLine2`, `city`, `country`
- `isActive` (default `true`)
- `version` (default `1`) for optimistic concurrency control
- `deactivatedAt`, `deactivatedBy`, `deactivationReason` for soft-deactivation tracking
- A composite unique constraint `@@unique([tenantId, name])` to prevent duplication per tenant.

## API Endpoints (Admin-only)

- **`GET /customers`**: Returns all customers for the specified tenant.
- **`POST /customers`**: Creates a new customer. Requires `name`.
- **`PATCH /customers/:id`**: Updates customer fields. Requires matching `version` for optimistic concurrency.
- **`PATCH /customers/:id/active`**: Toggles activation status. If deactivating, `reason` is required. Requires matching `version`.

_Note: All mutations are fully scoped to the `tenantId` and create entries in the `AuditLog` containing changed fields._

## Frontend Offline Architecture

### 1. Offline Database Model

IndexedDB schema was upgraded to version 3, introducing the `customers` object store (Key: `id`) with indexes on `name`, `isActive`, and `syncState`. The local model, `LocalCustomer`, carries a `syncState` of `PENDING`, `SYNCED`, `CONFLICT`, or `ERROR`.
Data retrieval happens exclusively via `CustomerLocalRepo` representing a unidirectional data flow (no UI component bindings to direct HTTP requests).

### 2. Outbox Operations

Customer mutations enqueue items in the outbox mapping to three core operations:

- `CUSTOMER_CREATE`
- `CUSTOMER_UPDATE`
- `CUSTOMER_SET_ACTIVE`

### 3. Sync Logic & Atomic Remapping

The `SyncDispatcherService` listens for outbox items and dispatches HTTP requests via `AdminCustomersService`.

- **On `CUSTOMER_CREATE` success:** The dispatcher executes an _Atomic ID Remap_, swapping the local provisional UUID with the server-acknowledged CUID in the IndexedDB store. It also scans the pending outbox items and remaps any dependent relationships.
- **On `CUSTOMER_UPDATE` and `CUSTOMER_SET_ACTIVE` success:** Local items are overwritten with truth from the server and marked `SYNCED`.

### 4. Conflict Handling & 409 Behavior

If the API rejects a requested mutation with an HTTP `409 Conflict` due to an outdated `version` field, the sync orchestrator intentionally halts processing for that entity to preserve state. The outbox item and local record are flagged as `CONFLICT`. The user must manually "Refresh from server" within the UI to reload the active state from the API and remap their changes iteratively.
