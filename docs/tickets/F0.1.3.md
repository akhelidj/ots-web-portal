# F0.1.3 Offline Session & Auth Behavior

## Overview

This document enforces the system rules for identifying user sessions efficiently, persisting them across application reloads, and ensuring deterministic functionality during offline operations.

## Session State

The internal portal tracks user validity exclusively through a short-lived JSON Web Token (JWT) strictly stored in standard `localStorage` (key: `auth_token`).

**Token Expiry Lifecycle:**

- `isAuthenticated$` is derived on application initialization (refresh) based on whether `localStorage` holds a valid JWT where `exp` is in the future.
- If a valid token expires _while_ the application is open, `isAuthenticated$` does not pro-actively emit a state change on an internal timer (v1 rule).
- However, critical workflows like `OutboxService` explicitly re-check token validity on-access (`session.isAuthenticated` sync getter) before pushing queued actions to prevent dispatches.
- If access evaluates to an expired state, syncing halts. The user can simply refresh the page to observe the full unauthenticated gating restrictions.

No API call is dispatched to calculate `isAuthenticated$`. This allows the application to retain session validity across disconnected states purely based on the local system clock and token configuration.

## Gating Policies (Feature Development Rules)

### In-Place Auth Checks

Component boundaries correctly enforce access restrictions through `@angular/router` functional guards (`auth.guard.ts`). However, rather than managing unauthenticated redirects, we utilize **in-place UI placeholders**.

- **Rule:** Do NOT introduce an unauthenticated route (i.e., `/sign-in` or `/unauthenticated`).
- When a user navigates to an internal route, the guard returns `false` to safely unmount feature loading.
- Simultaneously, the `ShellComponent` evaluates `!(isAuthenticated$ | async)` and gracefully swaps the internal `<router-outlet>` with the standard `<app-auth-required-placeholder>`.

## Sync & Offline Dependencies

The Offline Infrastructure specified in F0.1.2 relies heavily on the presence of a valid session to securely execute queued modifications.

1. **Sync Runner (`SyncOrchestratorService`):** The runner will entirely back off and pause loop evaluations if `isAuthenticated$` emits false. To trigger a queue processing sequence, it universally demands both an online network and a validated local token.
2. **Defensive Outbox Constraints (`OutboxService`):** Because race conditions are possible, the outbox processor proactively exits early on `processQueue()` if the synchronous token lookup determines validity has expired.

## Logout & Data Persistence

Calling `.logout()` correctly invalidates the current session by wiping the `<portal url>` `localStorage`.
**CRITICAL:** IndexedDB offline stores (e.g., `serial_numbers`, `inspection_reports`, or pending mutations) must **never** be wiped during logical logout operations in `v1`. The persistent stores represent locally queued labor and domain references that survive token timeouts.
