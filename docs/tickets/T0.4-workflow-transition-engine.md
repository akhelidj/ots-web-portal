# T0.4 Workflow Transition Engine - Verification & Policy

## 1. Final Transition Policy

The implementation strictly follows the Authoritative State Transition Matrix.

### InspectionReport

| From Status          | To Statuses               | Roles                        | Special Actions              |
| -------------------- | ------------------------- | ---------------------------- | ---------------------------- |
| DRAFT                | RECEIVED                  | Admin, Receiver              |                              |
| DRAFT                | ON_HOLD, CLOSED           | Admin, Supervisor            |                              |
| RECEIVED             | READY_FOR_CLEANING        | Admin, Receiver, Supervisor  |                              |
| RECEIVED             | ON_HOLD, CLOSED           | Admin, Supervisor            |                              |
| READY_FOR_CLEANING   | READY_FOR_INSPECTION      | Admin, Receiver, Supervisor  |                              |
| READY_FOR_CLEANING   | ON_HOLD, CLOSED           | Admin, Supervisor            |                              |
| READY_FOR_INSPECTION | IN_INSPECTION             | Admin, Supervisor, Inspector |                              |
| READY_FOR_INSPECTION | ON_HOLD, CLOSED           | Admin, Supervisor            |                              |
| IN_INSPECTION        | PENDING_APPROVAL          | Admin, Inspector             | Validation: >0 SerialNumbers |
| IN_INSPECTION        | ON_HOLD                   | Admin, Supervisor, Inspector |                              |
| IN_INSPECTION        | CLOSED                    | Admin                        |                              |
| PENDING_APPROVAL     | IN_INSPECTION, APPROVED   | Admin, Supervisor            |                              |
| PENDING_APPROVAL     | ON_HOLD, CLOSED           | Admin, Supervisor            |                              |
| APPROVED             | ON_HOLD, CLOSED           | Admin, Supervisor            |                              |
| APPROVED             | IN_INSPECTION             | Admin                        | Reopen: Reason + Snapshot    |
| ON_HOLD              | _Previous Status_, CLOSED | Admin, Supervisor            | Restore needs match previous |
| CLOSED               | APPROVED, IN_INSPECTION   | Admin                        | Reopen: Reason + Snapshot    |

### ChildReport

| From Status      | To Statuses      | Roles             | Special Actions            |
| ---------------- | ---------------- | ----------------- | -------------------------- |
| DRAFT            | IN_INSPECTION    | Inspector         |                            |
| IN_INSPECTION    | PENDING_APPROVAL | Inspector         |                            |
| PENDING_APPROVAL | APPROVED         | Admin, Supervisor | Validation: >0 Attachments |
| APPROVED         | CLOSED           | Admin, Supervisor |                            |
| APPROVED         | IN_INSPECTION    | Admin             | Reopen: Reason + Snapshot  |

## 2. Verification Logic

The following requests demonstrate the verification of the engine.

### Prerequisites

- Base URL: `http://localhost:3000`
- Headers: `Authorization: Bearer <TOKEN>`

### Scenario 1: Security (Customer Role)

**Request**:
`POST /inspection-reports/:id/transition` as Customer

```json
{ "toStatus": "RECEIVED" }
```

**Expected**: `403 Forbidden`

### Scenario 2: Parent Happy Path

1. **Inspector** moves `DRAFT` -> `RECEIVED`.
   - **Expected**: `403 Forbidden` (Inspector cannot move Draft).
2. **Receiver** moves `DRAFT` -> `RECEIVED`.
   - **Expected**: `200 OK`, Status: `RECEIVED`.
3. **Inspector** moves `IN_INSPECTION` -> `PENDING_APPROVAL` (Warning: No Serials).
   - **Expected**: `400 Bad Request` ("No serial numbers added").
4. **Supervisor** moves `PENDING_APPROVAL` -> `APPROVED`.
   - **Expected**: `200 OK`, Status: `APPROVED`, `revisionNumber`: 1.

### Scenario 3: Child Constraints

1. **Supervisor** moves Child `PENDING_APPROVAL` -> `APPROVED` (No Attachments).
   - **Expected**: `400 Bad Request` ("At least one attachment is required").

### Scenario 4: Governance (On Hold & Reopen)

1. **Supervisor** moves `RECEIVED` -> `ON_HOLD` (No Reason).
   - **Expected**: `400 Bad Request` ("Reason is required").
2. **Admin** moves `APPROVED` -> `IN_INSPECTION` (Reopen).
   - **Expected**: `200 OK`, Status: `IN_INSPECTION`, `revisionNumber` incremented, Snapshot created.

## 3. Snapshot Structure

Snapshots are stored in `InspectionReportRevision` and `ChildReportRevision` with the exact JSON structure defined in the ticket (Header fields, Serials, Child Summaries / Attachments).
