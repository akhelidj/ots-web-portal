# F0.2.3 — Workflow Transitions UI (Offline-First)

## Objective

Implement a robust, dynamic UX supporting offline-enabled status transitions for Inspection Reports, securely mapping to an authoritative API workflow engine. Ensures strict tracking, audit logging, and tenant isolation, backed by complete integration to optimistic concurrency control (`409`) loops and Outbox dispatch processing.

## Scope of Work

### Architectural Guardrails

- **Offline-First**: Ensure the system does not overwrite optimistic state prematurely. Uses `pendingTransitionToStatus` to visually articulate pending states without artificially disrupting the source of truth of an Inspection Report.
- **Performance Optimization**: UI pulls deep history arrays lazily/isolated (e.g., specific to the detail scope viewed) rather than aggressively pulling lists across N+1 entities during initial database cache hydration.
- **Resiliency**: Rejects `400` logic strictly in the UI by halting processing, capturing explicit logic errors, and automatically wiping `pendingTransitionToStatus` assumptions natively. Retries automatically on network disruption; alerts user locally on explicit `409` version conflicts.

3.  **Strict Validation Execution:**

4.  **Offline Verification:**

    - Trigger an allowable Status Transition.
