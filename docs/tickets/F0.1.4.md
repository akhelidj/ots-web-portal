# F0.1.4 Admin User Management MVP

## Data Flow Pattern Overview
This feature relies heavily on strict offline-first methodologies. 
Data is never rendered directly from the HTTP service. Instead, the UI (`AdminUsersComponent`) binds exclusively to the local IndexedDB representation wrapper (`AdminUsersService.users$`).

**Read-Through Cache:**
- On initialization, `AdminUsersService` aggressively pulls the `LocalUser` collection from IndexedDB to drive the initial rendering context, completely independent of browser connectivity capabilities.
- Simultaneously, if `isOnline` correctly evaluates active networking, an HTTP hook attempts to `GET /api/users`.
- If successful, results are synchronously batch written down directly into the local `UserLocalRepo` (overwriting un-modified cached records with Server truths).
- Finally, `AdminUsersService` triggers a secondary refresh loop across its UI `BehaviorSubject` pushing the most authentic view available immediately over to the user.

**Write-Through Outbox:**
- Modifying entities immediately overrides the local repo value and changes local flags indicating `syncState: 'PENDING_UPDATE' || 'PENDING_CREATE'`, offering real-time zero-lag responses back to operations.
- Queued actions are stacked transparently onto `OutboxService`. 

## Outbox Integration Mapping

### Payload Definition: `USER, CREATE`
When generating users offline, pseudo-random UUIDs prepended safely with metadata (`local-...`) serve immediately to join the `entityId` reference correctly without database collisions.
```json
{
  "entityType": "USER",
  "operation": "CREATE",
  "payload": {
    "email": "receiver@example.com",
    "name": "Receiver Role Test",
    "role": "RECEIVER",
    "isActive": true
  }
}
```
**Atomic Temporal ID Remapping Architecture:** 
When the Dispatcher successfully establishes an HTTP POST creating the User, it orchestrates a precise atomic sequence:
1. `GET` the `tempUserId` Local Entity model.
2. `UPSERT` the precise server payload containing the authentic SQL-generated UUID.
3. `DELETE` the old `tempUserId` to preclude listing artifact dupes.
4. Finally, recursively replace trailing `OutboxService` queries pointing onto the old ID towards the freshly bound server value.

Because passwords are automatically and securely generated by the server via `crypto`, the sync dispatch pipeline emits them backwards onto the `tempPasswordSubject` channel, allowing the UI hook to display the password uniquely just once post-synchronization.

### Payload Definition: `USER, SET_ACTIVE`
```json
{
  "entityType": "USER",
  "operation": "SET_ACTIVE",
  "payload": {
    "isActive": false
  }
}
```

## Conflict Resolution & Retries
By design in `v1`, if the user triggers an identical state overwrite on HTTP `PATCH /users/:id/active` representing the identical flag sequence elsewhere concurrently, the DB behaves predictably via a fast-fail 409 override.
If any Outbox sequence results directly in a 409 API `ConflictException`, the sync process entirely halts, placing the Queue into a strict `CONFLICT` block preventing cascade invalidations. Currently, resolution dictates deleting the item via manual debug flows or waiting for explicit UI management endpoints to cleanly evict them. Retries automatically occur dynamically on alternative transient statuses like a 500 Network reset.
