# F0.2.5 - Disposition + Pending Approval Gating

## Overview
This feature implements the offline-first collection of `disposition` during the inspection process and enforces server-authoritative validation rules before an Inspection Report can transition to `PENDING_APPROVAL`.

### Goal
- Collect dispositions for `SerialNumber` records natively within the `inspectionData` layer without adding new schema columns.
- Prevent progression of reports to `PENDING_APPROVAL` unless all associated serial numbers have complete inspection data (specifically for `DRILL_PIPE_REPORT` templates) and an assigned `disposition`.
- Preserve the ability to work entirely offline, surface structured `400 Validation Errors` smoothly on sync, and retain offline retry contexts without losing user intentions.

## Architectural Constraints Implemented
- **No Schema Modifications:** Disposition lives inside `inspectionData.disposition`, keeping the `SerialNumber` table lean.
- **Strict DTO Mapping:** `PATCH /api/serial-numbers/:id` explicitly expects `{ inspectionData?: any, version: number }`. (Note: `inspectionJson` was changed to `inspectionData` to align payloads natively).
- **Atomic Optimistic Concurrency:** `updateSerialNumber` performs a single atomic Prisma update using `{ id, tenantId, version }` in the where clause and increments version in the same statement.
- **Tenant Scope Locks:** The API fetches the parent report strictly filtered by the user's `tenantId` to ensure safe status checks (`APPROVED` or `CLOSED` blocks mutation).
- **Server Authoritative Template Checks:** `InspectionReportWorkflowService.transition()` queries serial numbers directly from the DB. It dynamically checks if the `templateKey` is `DRILL_PIPE_REPORT` before asserting the presence of keys defined in `DRILL_PIPE_FIELDS`.

## Verification Steps (Offline-Realistic)

1. **Setup & Initialization**
   - Log in as an Inspector (`alice`).
   - Create a new Inspection Report using the `DRILL_PIPE_REPORT` template.
   - Transition it to `IN_INSPECTION`.
   - Add two Serial Numbers: `SN-001`, `SN-002`.

2. **Offline Data Entry (Missing Required Fields)**
   - Go offline (turn off network or stop API).
   - Open `SN-001`. Set disposition to `PASS`, but leave `Outer Diameter` empty. Save.
   - Notice the outbox queues the `SN_UPDATE_INSPECTION` operation.

3. **Offline Workflow Gating (Simulated Fast Failure)**
   - Still offline, click `PENDING_APPROVAL`.
   - The UI queues the transition locally.
   - Go online (restart API/network).
   - Sync Trigger.

4. **Error Handling & Retry Loop**
   - The sync dispatcher will push the serial updates and the transition request.
   - The `PENDING_APPROVAL` transition will fail with `400 Bad Request` (`VALIDATION_FAILED`) from the backend because `SN-001` lacks the required `outerDiameter` and `SN-002` lacks a disposition altogether.
   - The UI surfaces this error seamlessly. Crucially, the transition remains marked as `ERROR` in the local DB. It is **not** silently discarded.
   
5. **Successful Resolution**
   - Open `SN-001`, fill out `Outer Diameter`.
   - Open `SN-002`, fill out all required fields and set disposition to `REWORK`.
   - Wait for sync.
   - Click `PENDING_APPROVAL` again.
   - The report transitions successfully online securely driven by server-authoritative logic.

## Technical Nuances
- **Disposition Logic**: Disposition must be explicitly selected by the inspector before transition. It is strictly persisted into `inspectionData.disposition` locally (and mapped natively to the backend).
- **Outbox Stability:** `sync-dispatcher.service.ts` catches `400` validation errors and marks `syncState: 'ERROR'` instead of unceremoniously deleting the entity context. This enables offline-first safety for complex state machines rejecting premature transitions.
